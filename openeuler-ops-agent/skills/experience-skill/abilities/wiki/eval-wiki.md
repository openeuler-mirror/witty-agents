# eval-wiki

## 触发条件

当满足以下任一条件时触发本能力：

- 用户明确提出"评估 Wiki 质量"、"检查 Wiki 是否有用"、"验证 Wiki 召回率"等意图。
- 存量 Wiki 体量较大时，定期主动提醒用户对 Wiki 进行质量核验。
- 新建或优化 Wiki 后，验证 Wiki 是否达到预期质量。

## 评估维度

Wiki 质量评估围绕以下四个维度展开：

| 维度 | 说明 | 评估方式 |
| ---- | ---- | ------- |
| **召回命中率** | Wiki 在关键词检索中能否被准确召回 | 随机抽样 + 检索验证 |
| **内容实用性** | Wiki 内容是否能解决实际问题、提供有效参考 | 问答核验 + 场景匹配 |
| **内容准确性** | Wiki 中的信息是否正确、是否有过时内容 | 交叉验证 + 源文档对比 |
| **可读性** | Wiki 的格式、结构、语言表达是否清晰易懂 | 结构化评分 |

## 执行流程

### 第一步：确定评估范围

按需选择评估范围：

```bash
cd scripts

# 评估全部 Wiki
uv run experience-skill list-experiences --type WIKI

# 按关键词筛选评估范围
uv run experience-skill search-experiences \
    --query "<主题关键词>" \
    --type WIKI \
    --top-k 20
```

无法一次评估全部 Wiki 时，优先选择：

- 最近新增的 Wiki（created_at 排序）
- 高频使用的 Wiki（is_hot = true）
- 用户指定的重点领域 Wiki

### 第二步：召回命中率评估

随机抽取 N 个 Wiki（建议 N≥5），对每个 Wiki 执行以下核验：

1. **关键词召回测试**：

   ```bash
   # 取 Wiki 的 name 和 keywords 作为查询词
   uv run experience-skill search-experiences \
       --query "<Wiki 名称或首个关键词>" \
       --type WIKI \
       --top-k 10
   ```

   - 验证目标 Wiki 是否出现在 Top-K 结果中。
   - 记录排名位置（首位召回得分最高）。

2. **语义召回测试**：

   使用 Wiki 描述文本中的自然语言句子作为查询词：

   ```bash
   uv run experience-skill search-experiences \
       --query "<Wiki 描述中的核心语句>" \
       --type WIKI \
       --top-k 10
   ```

   - 验证语义相关的 Wiki 是否被召回。

3. **召回评分**：

   | 评分 | 标准 |
   | ---- | ---- |
   | 优秀 | 关键词和语义查询均能在 Top-3 召回 |
   | 合格 | 至少一种查询方式能在 Top-5 召回 |
   | 不合格 | 两种查询方式均无法在 Top-10 召回 |

### 第三步：内容实用性评估

对每个抽样的 Wiki，设计 1-3 个与 Wiki 内容相关的实际问题：

1. **问题设计原则**：
   - 问题应能通过 Wiki 内容直接或间接回答。
   - 覆盖 Wiki 的核心知识点和边界场景。

2. **实用性评分**：

   | 评分 | 标准 |
   | ---- | ---- |
   | 优秀 | Wiki 内容能直接解答所有测试问题，结论明确可操作 |
   | 合格 | Wiki 内容覆盖大部分问题，但部分回答不够完整或需要补充 |
   | 不合格 | Wiki 内容无法有效解答测试问题，信息不足或偏离主题 |

### 第四步：内容准确性评估

1. **交叉验证**：
   - 若 Wiki 的 YAML front matter 中有 `references` 字段，对比源文档验证关键数据、结论是否准确。
   - 若无 references，结合网络搜索或知识库交叉确认核心观点。

2. **时效性检查**：
   - 检查引用的工具版本、API 接口、命令语法是否仍适用。
   - 标记过时内容。

3. **准确性评分**：

   | 评分 | 标准 |
   | ---- | ---- |
   | 优秀 | 核心内容经交叉验证确认无误，无过时信息 |
   | 合格 | 存在少量非关键性偏差或轻微过时内容 |
   | 不合格 | 存在明确错误信息或严重过时导致误导 |

### 第五步：可读性评估

1. **结构检查**：
   - 是否有清晰的标题层级。
   - 段落划分是否合理，无大段文字堆砌。

2. **语言检查**：
   - 有无明显语病、歧义表达。
   - 专业术语是否准确、有无解释。

3. **可读性评分**：

   | 评分 | 标准 |
   | ---- | ---- |
   | 优秀 | 结构清晰、语言流畅、术语准确、格式规范 |
   | 合格 | 整体可读但存在小问题（个别段落过长、格式不统一等） |
   | 不合格 | 结构混乱、表达不清、严重影响阅读体验 |

### 第六步：生成评估报告

汇总四个维度的评分，生成评估报告：

```markdown
# Wiki 质量评估报告

## 基本信息
- 评估范围：<WIKI 数量> 个 Wiki
- 抽样数量：<N> 个
- 评估时间：<YYYY-MM-DD>

## 汇总得分

| Wiki 名称 | 召回命中率 | 内容实用性 | 内容准确性 | 可读性 | 综合评级 |
| --------- | --------- | --------- | --------- | ----- | ------- |
| wiki_1    | 优秀      | 合格      | 优秀      | 优秀   | 良好    |
| wiki_2    | 合格      | 优秀      | 合格      | 合格   | 合格    |
| wiki_3    | 不合格    | 不合格    | 合格      | 合格   | 待优化  |

## 待优化项

### wiki_1
- 关键词覆盖不足，建议补充"<keyword>"。

### wiki_3
- 召回全部失败，建议重新梳理 keywords 和 description。
- 内容过于简略，缺少核心操作步骤。
```

### 第七步：跟进优化

评估报告中标记为"待优化"的 Wiki，自动建议用户执行 `optimize-wiki` 流程进行迭代改进。

## 评估频率建议

| 场景 | 建议频率 |
| ---- | ------- |
| Wiki 总数 < 20 | 每季度全量评估一次 |
| Wiki 总数 20-100 | 每月抽样评估 20%，滚动覆盖 |
| Wiki 总数 > 100 | 每两周抽样评估 10%，优先评估热门 Wiki |
| 新建 Wiki 后 | 创建后 1 周内执行首次评估 |

## 与其他能力的协作

- **optimize-wiki**：评估发现问题后，触发优化流程修复。
- **merge-wiki**：评估发现同质化严重时，建议合并精简。
- **find-wiki**：评估过程中使用检索能力进行召回测试。
